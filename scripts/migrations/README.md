# Доступ администратора

## Применение

1. В Supabase → Authentication → Users убедитесь, что существует аккаунт
   `digidro.work@gmail.com`. Пароль и service role key в код добавлять не нужно.
2. В SQL Editor от имени `postgres` выполните `001-admin-access.sql` целиком.
   Миграция транзакционная и допускает повторное выполнение. Каталог и акции
   не удаляются. Если аккаунт не найден, изменения не применятся.
3. Выполните `verify-admin-access.sql`: проверки работают в транзакции и
   завершаются `ROLLBACK`, не сохраняя тестовые изменения.
4. Только после успешной миграции опубликуйте новую сборку приложения.
5. Войдите главным аккаунтом. При ошибке RPC приложение закрывает доступ,
   а не разрешает его по факту входа.

Роль хранится в `private.admin_users` и назначается только доверенным SQL
администратором. Браузер не имеет доступа к таблице ролей. `is_admin()`
возвращает только флаг доступа текущего пользователя. Роль `owner` пока даёт
те же права на каталог, что и `admin`; интерфейса управления ролями нет.

Публичное чтение не меняется. `service_role` и владелец БД по-прежнему обходят
RLS — такие ключи нельзя помещать в клиентские переменные `VITE_*`.

Старые скрипты пересоздания/очистки данных отозваны и удалены.
Правила работы со схемой описаны в `../README.md`.

## 002 — search_path функции обновления даты

`002-lock-updated-at-search-path.sql` подготовлен локально и **не применён
к рабочей БД**. Он фиксирует пустой `search_path` у существующей
`public.set_updated_at()`, не заменяя её тело и не меняя данные или триггеры.
Для применения к рабочей БД требуется отдельное разрешение.

Локально проверено на изолированной БД: повторное применение безопасно,
OID и тело функции и OID её триггеров сохраняются, данные не меняются.
Оба триггера обновляют дату после миграции; проверки административных прав
из `verify-admin-access.sql` по-прежнему проходят.

## Проверка рабочей базы — 28 октября 2026

Миграция применена через Supabase MCP к проекту `qlkgvdpvmwoeuehtaynb`
под именем `restrict_catalog_writes_to_admins`. Проверки CRUD главного
аккаунта, запрета записи для обычного пользователя/посетителя и защиты
таблицы ролей прошли на рабочей БД в откатываемой транзакции. Количество
строк и контрольные суммы каталога и акций до/после совпали:
20 категорий, 258 услуг, 5 акций.

Проверка Supabase Advisors отмечает ожидаемые свойства этой реализации:

- [RLS без политик у закрытой таблицы ролей](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy):
  это намеренный запрет клиентского доступа, а не недостающая публичная политика.
- [SECURITY DEFINER доступен anon](https://supabase.com/docs/guides/database/database-linter?lint=0028_anon_security_definer_function_executable)
  и [authenticated](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable):
  `is_admin()` намеренно вызывается политиками и интерфейсом. Она не принимает
  чужой UUID, не меняет данные и возвращает только флаг текущего пользователя;
  анонимный вызов возвращает `false`. `search_path` зафиксирован.

Также остались два предупреждения, существовавшие до миграции. В рамках
ограничения административной записи они не менялись:

- [Не зафиксирован search_path у set_updated_at](https://supabase.com/docs/guides/database/database-linter?lint=0011_function_search_path_mutable).
- [Не включена проверка утёкших паролей](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection).
